Study this project

For someone who wants to learn from this project rather than follow it: what to read in which order, the ideas you need, the words we use, how to run it yourself, and a few exercises.

Reading order

  1. Overview: what is learned, the measure, the pipeline diagram. 5 minutes.
  2. How it sees: the 175 numbers the net gets at a buy, and what only the search sees (nothing hidden: it reshuffles instead). 5 minutes.
  3. The model: why Dominion needs IS-MCTS, the network, the leaf value, the target, and the pictures of the real net (how sharp its policy is matters for everything after iteration 100). 15 minutes.
  4. Training: the progress chart and the goal table. Notice the line flattening at about 69% from iteration 100 on, and the "net alone" line almost catching the search. 5 minutes.
  5. Lessons and the Log (filter: Notes): every experiment and what it showed. 10 minutes. The Podcast tells the same story by ear.
  6. The code, in this order: c/az.c (search, select_puct, sim_decide, eval_priors: the whole algorithm in ~250 lines of C), az/net.py (the MLP and its gradient by hand), train.py (the loop), experiments/goal_check.py (how every claim is measured). 1–2 hours.

Key concepts

Search plus a net beats either alone, while they disagree

The net is fast intuition; the search is slow checking. AlphaZero's loop works because the search, guided by the net, finds better moves than the net would play, and the net then learns them. Here: at the warm start the search added 8 points (net 50% → search 58% vs the GA). What people get wrong: the loop only improves while the search can disagree with the net. Once the net predicts the searched buy 98% of the time, self-play mostly teaches the net what it already knows (see the "agreement" chart on Training).

Determinization and IS-MCTS

In a game with hidden cards, the search can't know the true deck order, so each simulation guesses one (de_hide) and the tree is keyed only by what the player has seen: the sequence of buys. Averaging over 400 guesses gives the value of a buy over the luck of the draw. Here: search() in c/az.c. What people get wrong: searching the single true deal ("cheating") looks much stronger in testing and is worthless in a real game.

PUCT and the prior

Each simulation picks the buy with the best "average result + cpuct × prior × √(total visits) / (1 + visits)". A buy the net gives 0.1% hardly ever gets visited, however good it is. Here: select_puct. What people get wrong: thinking more simulations always fix this. With a near one-hot prior, 400 or 1,600 simulations mostly confirm the net's choice; the prior temperature experiments on the Log test exactly this.

Leaf evaluation: value net vs rollout

When a simulation reaches a new position it must score it. A value net is cheap but here it is weak (the winner of a close Dominion game is hard to predict); a rollout to the end with the GA genome is unbiased but noisy. Mixing half and half beat both (58% vs 53% and 54% at 400 simulations). Where: lam in train.py, results/bake_leaf_*. What people get wrong: more search with a bad value net got worse (53% → 48% from 400 to 1,600 simulations): the search chases the net's errors.

The policy target

What the net learns to predict at each searched buy. AlphaZero uses the visit shares; this project uses the single buy the search chose (expert iteration). Why: Dominion's buys are often nearly equal, so the visit shares were mostly the net's own prior plus noise, and training on them collapsed the net (52% → 24% in one iteration, run r1). What people get wrong: the one-hot target has its own cost: it drives the policy towards certainty, which later starves the search of exploration.

Measuring a win rate honestly

A 200-game evaluation has a 95% interval of ±7 points; 1,000 games ±3. The best of many 200-game checks is flattered by luck (winner's curse). Here: per-iteration evaluation (the chart) vs the goal check (the table, fresh kingdoms every model sees the same). What people get wrong: reading a 3-point jump between two iterations as progress.

Same actions, different buys

Both players use the same GA genome for every non-buy decision, so a score above 50% is caused by the buys alone. Where: az_decide hands every non-buy decision to ga_decide. What people get wrong: comparing against an opponent that also plays its actions differently, and crediting the buys.

Reproduce it

On an 8-core laptop CPU (Intel i5-8250U, no GPU, 8 GB RAM), Linux, Python 3.14, gcc:

git clone --recursive https://github.com/JCA374/dominion-az-v1 && cd dominion-az-v1
python3 -m venv .venv && .venv/bin/pip install numpy pytest pillow matplotlib
.venv/bin/python -m pytest -q          # builds az.so (C, ~5 s) and runs the parity tests: "6 passed" in ~7 s
.venv/bin/python -u train.py --run mine --set iterations=10
    # warm start: 12,000 GA games + 8 epochs (~3 min), evaluation of net 0 (~3 min),
    # then ~4 min per iteration. Prints e.g.
    # iter 1: search Big M=0.84 Smith=0.73 Witch=0.66 GA ba=0.59 ...
.venv/bin/python experiments/goal_check.py runs/mine/net_10.npy --name mine10
    # 1,600 fresh games, ~2.5 min: results/goal_mine10.json, e.g. "score": 0.63 (GA base = 0.50)
.venv/bin/python experiments/goal_check.py runs/mine/net_10.npy --name mine10_net --sims 0   # the net alone, 1 s

Expect the score against the GA base to rise from ~58% (net 0 with search) to ~63–65% after 10 iterations, and to flatten near 69% after ~100 (about 7 hours).

Exercises

  1. Easy: what does search add? Run goal_check.py on the same net with --sims 0, 100, 400 and 1600. Plot score against simulations. Expect a large gain from 0 to 100 for net 0 and a small one for net 357. Why the difference?
  2. Easy: the leaf mix. Same net, --lam 0, 0.5, 1. With the warm-start net the mix won. Does the trained net's value head deserve more weight now?
  3. Medium: soften the prior. --ptemp 2 and --peps 0.25 flatten the net's prior inside the search (eval_priors in c/az.c). Measure the score and also how often the searched buy differs from the net's argmax. More disagreement is only useful if the score holds.
  4. Medium: the policy target. In train.py set target=0 (visit shares) for a run from the warm start and watch the "net alone" line in the first 3 iterations. Then try target=1 with c_scale 0.3. Expect the first to collapse; explain why with the visit counts of one decision.
  5. Hard: a better value target. The value head learns the final result (±1), a very noisy label. The search also records its root value Q for every decision (az/selfplay.py). Train the value on (z + Q) / 2 instead (az/net.py train), then repeat exercise 2. Does the net's value now earn a larger lam?
